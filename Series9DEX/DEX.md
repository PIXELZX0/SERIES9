# Series9DEX — 설계 명세서

> **프로젝트:** Series9 Decentralized Exchange
> **위치:** `series9/Series9DEX/`
> **상태:** 초안 (Draft v0.3)

---

## 1. 개요 (Overview)

**Series9DEX**는 **두 ERC-20 토큰** 간의 탈중앙화 거래소(DEX)입니다. 페어의 양쪽 토큰 모두 **어떤 ERC-20** 이든 자유롭게 조합할 수 있습니다 (**ANY/ANY 페어**). **SER9 또한 ERC-20 (또는 그 래퍼)** 이므로 페어의 한쪽 토큰으로 자연스럽게 참여할 수 있으며, 반대로 SER9 없이 다른 ERC-20 끼리의 페어도 문제없이 생성·운영됩니다.

AMM 기반의 시장가 주문과, **완전 온체인 오더북(on-chain orderbook)** 기반의 지정가 주문을 모두 지원합니다.

모든 거래 페어는 고유한 **Pair ID** 로 식별되며, 해당 ID 는 페어에 속한 **풀(Pool)** 을 조회·연결하는 키로 사용됩니다.
**수수료(fee rate)는 풀을 생성하는 사람이 직접 선택**할 수 있어, 같은 페어라 하더라도 풀마다 다른 수수료 정책을 운영할 수 있습니다.
풀 생성자가 설정한 lpFee 의 **0.1% 는 프로토콜 수수료**로 회수되며, 나머지 99.9% 는 풀의 LP 등에게 분배됩니다.

## 2. 핵심 구조 (Core Architecture)

```
Series9DEX
├── Pairs (페어 목록)
│   ├── Pair ID  ──→  Pair Metadata (tokenA, tokenB, ...)
│   │
│   ├── Spot Pool (현물 풀)
│   │     ├── tokenA reserves
│   │     ├── tokenB reserves
│   │     ├── lpFeeRate  (풀 생성자가 설정)
│   │     └── protocol cut = lpFeeRate × 0.1% → ProtocolTreasury
│   │         LP share    = lpFeeRate × 99.9% → LP
│   │
│   └── Futures Pool (선물 풀)
│         ├── Long positions
│         ├── Short positions
│         └── Collateral (USDC 등)
│
└── Orderbook (주문 시스템)  ── ALL ON-CHAIN
    ├── Market Orders  (시장가)
    └── Limit Orders   (지정가, 전량 온체인)
```

## 3. 페어 (Pairs)

### 3.1 페어 구성
- 모든 페어는 **두 ERC-20 토큰**의 조합으로 구성됩니다 (**ANY/ANY 페어 지원**).
- **SER9** 도 ERC-20 (또는 그 래퍼) 이므로 페어의 **어느 한쪽**이든 자유롭게 참여할 수 있고, **SER9 없이** 다른 ERC-20 끼리의 페어(예: `USDC / WETH`) 도 제약 없이 생성할 수 있습니다.
- 두 토큰의 주소가 동일할 수 없습니다 (셀프 페어 금지).
- 예시:
  - `SER9 / USDC`
  - `SER9 / WETH`
  - `USDC / WETH`
  - `WBTC / USDC`
  - `SER9 / 프로젝트 토큰 X`

### 3.2 Pair ID
- 각 페어는 **고유한 `pairId`** (예: `bytes32` 또는 `uint256`) 를 가집니다.
- **용도:** 동일한 페어에 속한 모든 풀(현물/선물)을 조회·연결하기 위한 **공통 식별자**.
- 페어 ID 는 풀 컨트랙트에 저장되며, 새 풀을 추가할 때 동일한 페어 ID 를 공유합니다.
- 페어 ID 는 **두 토큰 주소를 정렬(낮은 주소가 `tokenA`, 높은 주소가 `tokenB`) 한 뒤** keccak256 으로 계산합니다. 이렇게 정규화하면 페어가 어느 방향으로 생성되든(예: `WETH/USDC` vs `USDC/WETH`) 동일한 `pairId` 가 도출되어 중복 생성이 방지됩니다.
- 페어 등록/풀 생성 시점에 `tokenA < tokenB` 가 되도록 자동 정렬되며, 컨트랙트도 동일하게 정규화합니다.

```
// tokenA, tokenB 가 address(0) 가 아니고 서로 다르며 tokenA < tokenB 임이 전제
pairId = keccak256(abi.encodePacked(tokenA, tokenB))
```

> 참고: `feeTier` 는 페어 ID 생성에서 제외됩니다. 같은 페어라도 **풀마다 다른 수수료**를 가질 수 있기 때문입니다.

### 3.3 페어 ↔ 풀 매핑
- 단일 페어 ID 는 **여러 풀**을 가질 수 있습니다.
  - 현물 풀 N개 (수수료/세팅 다르게)
  - 선물 풀 N개 (만기/마진 종류별)
- 페어 ID 로 모든 풀을 조회할 수 있어야 합니다.

## 4. 주문 유형 (Order Types)

### 4.1 시장가 주문 (Market Order)
- AMM 의 현재 호가(현물 풀 reserves 기반)로 즉시 체결.
- 슬리피지 허용치(`minAmountOut`) 지정 필수.
- 페어 ID → 해당 현물 풀 라우팅.
- 수수료는 **선택된 풀의 `lpFeeRate` + 프로토콜 수수료 0.1%** 가 적용됩니다.

### 4.2 지정가 주문 (Limit Order) — 전량 온체인
- 원하는 가격에 도달했을 때 자동 체결.
- **호가창(Orderbook) 자체가 온체인에 저장·관리**됩니다. 오프체인 relayer 를 두지 않으며, 외부 운영 주체 없이 누구나 체인만 보고 호가를 조회·체결할 수 있습니다.
- 페어 ID 와 목표 가격(`limitPrice`)을 주문에 포함.

#### 온체인 오더북 구조 (예시)
```
Orderbook (pairId 별)
├── bids[price]        ── 매수 주문 누적 (price → totalAmount)
└── asks[price]        ── 매도 주문 누적 (price → totalAmount)
```
- 가격 단위(price tick)는 풀 생성 시 설정.
- 주문 등록/취소/매칭 모두 트랜잭션으로 발생 — 가스 비용 발생.
- 누구나 `Orderbook(pairId).bestBid()` / `bestAsk()` 로 호가 조회 가능 (view).
- 매칭 로직은 동일 페어의 **현물 풀(AMM)** 과 대조하여 자동 체결.

#### Limit Order 필드 (예시)
| 필드 | 타입 | 설명 |
|---|---|---|
| `maker` | `address` | 주문 등록자 |
| `pairId` | `bytes32` | 페어 ID |
| `side` | `enum (BUY / SELL)` | 매수/매도 |
| `price` | `uint256` | 지정 가격 |
| `amount` | `uint256` | 주문 수량 |
| `expiry` | `uint256` | 만료 시각 |
| `status` | `enum (OPEN / FILLED / CANCELLED / EXPIRED)` | 주문 상태 |

#### 온체인 오더북의 장단점
- ✅ **장점:** 단일 진실 공급원, 검열 저항성, 투명한 호가, relayer 의존성 없음.
- ⚠️ **단점:** 주문 등록/취소/매칭 모두 가스 비용. (Monad 등 고처리량 L1 에서 완화 기대)

## 5. 풀 (Pools)

### 5.1 현물 풀 (Spot Pool)
- **AMM 기반** 유동성 풀 (Uniswap V2/V3 스타일).
- 동일 페어 ID 안에서 토큰 ↔ 토큰 즉시 스왑.
- 유동성 제공자(LP) 가 유동성 공급 및 fee 분배.

### 5.2 선물 풀 (Futures Pool)
- **레버리지 포지션** 관리 (Long / Short).
- 마진 담보 기반.
- 펀딩레이트, 청산 메커니즘, 만기 처리 등 포함.
- 페어 ID 로 현물 풀과 연결되어 가격 오라클 공유.
- **수수료 정책: 현물 풀과 동일** — 풀 생성자가 `lpFeeRate` 선택 + 그 `lpFeeRate` 의 **0.1% 가 프로토콜 수수료**, 99.9% 가 LP 로 분배.

### 5.3 현물 ↔ 선물 풀 관계
| 항목 | 현물 풀 | 선물 풀 |
|---|---|---|
| 용도 | 즉시 스왑 | 레버리지 포지션 |
| 가격 결정 | reserves 비 (x*y=k) | 오라클 / 마크 가격 |
| 페어 ID 공유 | ✅ | ✅ |
| 수수료 설정 | **풀 생성자가 `lpFeeRate` 선택** (그 중 0.1% 가 프로토콜, 99.9% 가 LP) | **현물과 동일** (생성자 선택 + lpFee 의 0.1% 가 프로토콜) |
| LP / 트레이더 | LP (유동성 공급) | 트레이더 (포지션 진입) |

## 6. 수수료 (Fee) — 풀 생성자 결정 + 프로토콜 컷(0.1% of lpFee)

> **원칙 1:** 수수료는 고정 티어(fee tier) 가 아니라, **풀을 생성하는 사람이 풀 생성 시점에 직접 선택**합니다.
> **원칙 2:** 풀 생성자가 설정한 `lpFeeRate` 의 **0.1%** 가 **프로토콜 수수료**로 프로토콜 금고(`ProtocolTreasury`) 에 회수됩니다. 나머지 99.9% 는 LP 등에게 분배됩니다.

### 6.1 적용 범위
- **현물 풀:** 풀 생성 트랜잭션의 파라미터로 `lpFeeRate` 를 지정. (예: `3 / 1000` = 0.3%)
- **선물 풀:** **현물과 동일한 수수료 정책** 적용 — 풀 생성자가 `lpFeeRate` 지정 + 그 lpFee 의 0.1% 가 프로토콜.
- **시장가/지정가 주문:** 거래가 라우팅되는 **해당 풀의 `lpFeeRate`** 가 자동 적용.

### 6.2 수수료 분배 구조
거래 1회당 차감되는 총 수수료 = `lpFeeRate` (거래량 대비). 그 안에서:
- **프로토콜 수수료** = `lpFeeRate × 0.1%` (= `lpFeeRate × 0.001`) → `ProtocolTreasury`
- **LP 수수료** = `lpFeeRate × 99.9%` (= `lpFeeRate × 0.999`) → 해당 풀의 LP

| 구분 | 비율 | 수취자 |
|---|---|---|
| **프로토콜 수수료** | `lpFeeRate` 의 **0.1%** (= `lpFeeRate × 0.001`) | **프로토콜 금고 (`ProtocolTreasury`)** |
| LP 수수료 | `lpFeeRate` 의 **99.9%** (= `lpFeeRate × 0.999`) | 해당 풀의 LP |
| **총 수수료** | `lpFeeRate` | — |

#### 예시
| `lpFeeRate` (풀 생성자 설정) | 프로토콜 (0.1% of lpFee) | LP (99.9% of lpFee) |
|---|---|---|
| 0.10% (10 bps) | 0.0001% (0.01 bps) | 0.0999% (9.99 bps) |
| 0.30% (30 bps) | 0.0003% (0.03 bps) | 0.2997% (29.97 bps) |
| 1.00% (100 bps) | 0.0010% (0.10 bps) | 0.9990% (99.90 bps) |

### 6.3 LP 수수료 분배
- 풀 생성 시 설정된 fee 분배 정책(`feeRecipient`, LP 비중 등) 사용.
- 기본값(미설정 시): LP 에 100% 분배.

### 6.4 제약
- **프로토콜 컷 비율 (0.1%):** 고정 (거버넌스로 변경 가능 — 추후 결정).
- **LP 수수료 가드레일:** 0% ≤ `lpFeeRate` ≤ 5% (거버넌스/owner 가 관리).
- 결과적으로 풀의 **총 수수료**는 `lpFeeRate` 그대로 (0% ~ 5% 범위).
